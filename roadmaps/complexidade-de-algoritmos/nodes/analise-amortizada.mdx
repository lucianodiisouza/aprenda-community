Às vezes, um algoritmo tem operações **muito caras** que acontecem
**raramente** - e operações baratas que acontecem o tempo todo. O pior
caso isolado (Big O) parece assustador, mas a **média ao longo do
tempo** é muito melhor. Aí entra a **análise amortizada**: distribuir
o custo das operações caras por todas as operações, para encontrar o
**custo médio real**.

O exemplo canônico é o **array dinâmico** (a `ArrayList` do Java, o
`list` do Python, o `Array` do JavaScript, por baixo dos panos).

Como funciona um array dinâmico:

1. Você tem um array interno de tamanho `capacidade`.
2. Insere elementos. Cada `push` é **O(1)**.
3. Quando o array enche, ele **realoca**: cria um array novo, com o
   **dobro** da capacidade, e copia todos os elementos. Isso é **O(n)**
   - lento.
4. Aí tem "espaço de sobra" para muitas inserções futuras.

A realocação é cara, mas acontece **cada vez menos frequente** conforme
o array cresce. Análise:

- 1ª realocação: do tamanho 1 para 2 - copia 1 elemento.
- 2ª: de 2 para 4 - copia 2.
- 3ª: de 4 para 8 - copia 4.
- 4ª: de 8 para 16 - copia 8.
- ... e assim por diante.

Total de cópias após `n` inserções: `1 + 2 + 4 + ... + n/2 ≈ n`. Ou seja,
**O(n) no total** para `n` inserções - ou **O(1) amortizado por inserção**.

Compare:

- **Big O (pior caso):** `push` é **O(n)** (quando tem que realocar).
- **Análise amortizada:** `push` é **O(1) por operação** ao longo do tempo.

Os dois estão "certos" - medem coisas diferentes. Big O pergunta "qual
o pior que pode acontecer em UMA operação?". Análise amortizada pergunta
"se eu fizer MUITAS operações, qual o custo médio de cada uma?".

Outros exemplos de análise amortizada:

- **`HashMap` (tabela hash) com redimensionamento:** realocar é O(n),
  mas a amortização é O(1) por inserção (mesma lógica do array dinâmico).
- **`Union-Find` com path compression:** cada operação `find` é
  praticamente O(1) amortizado (com union by rank).
- **`Splay tree` (árvore auto-ajustável):** operações são O(log n)
  amortizado, embora possam ser O(n) no pior caso individual.

Três métodos clássicos de análise amortizada:

- **Método do agregado (aggregate):** some o custo total de `n` operações
  e divida por `n`. Foi o que fizemos acima.
- **Método contábil (accounting):** algumas operações "poupam" créditos
  que operações futuras mais caras "gastam".
- **Método do potencial (potential):** define uma "função de potencial"
  da estrutura de dados; o custo amortizado é o custo real mais a
  variação do potencial.

> Dica: quando alguém disser "essa operação é O(1) amortizado", lembre
> que **pior caso** ainda pode ser ruim. Um array dinâmico é O(1)
> amortizado, mas se sua latência individual importa (ex: render de
> frames), a realocação pode causar **um frame travado** mesmo que
> "em média" esteja tudo bem. Saber analisar **qual métrica importa**
> é parte de usar Big O com maturidade.

- **Análise amortizada** mede o custo médio ao longo de muitas operações,
  não o pior caso de uma única.
- **Array dinâmico** é o exemplo clássico: `push` é O(n) no pior caso
  (realocação) e O(1) amortizado (a realocação é diluída).
- **Big O e análise amortizada respondem perguntas diferentes** - e
  podem coexistir sem contradição.
- **Use o método certo para a pergunta certa.** Latência individual
  (Big O) vs. throughput médio (amortizado) são problemas diferentes.

Você chegou no fim do nível **avançado**. No próximo nó, é o **projeto
final**: aplicar tudo isso para comparar, na prática, algoritmos que
resolvem o mesmo problema - e ver a diferença aparecer nos números.
