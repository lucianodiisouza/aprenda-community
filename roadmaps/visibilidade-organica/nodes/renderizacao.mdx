Toda página que existe na internet chega ao buscador em algum formato. A
decisão que você toma no stack — se o React monta a tela no navegador, no
servidor ou no build — decide se esse formato tem o seu conteúdo dentro.

## O essencial 🟢

O crawler pede uma URL e recebe **HTML**. Tudo que você escreve no seu
frontend precisa chegar nesse HTML para o buscador ler.

Existem três estratégias clássicas:

**CSR (Client-Side Rendering)** — o servidor entrega um "app shell" e o
JavaScript monta a página depois, no navegador de quem chegou:

```html
<!doctype html>
<html lang="pt-BR">
  <head>
    <meta charset="utf-8" />
    <title>Aurora</title>
  </head>
  <body>
    <div id="root"></div>
    <script src="/assets/app.js"></script>
  </body>
</html>
```

Repare no que o crawler recebeu: um `<div id="root">` **vazio**. O título
"Planos da Aurora", os preços, os textos de FAQ — nada disso está no HTML.
Estão no bundle de JavaScript.

**SSR (Server-Side Rendering)** — o servidor monta a página antes de enviar.
O HTML chega pronto:

```html
<!doctype html>
<html lang="pt-BR">
  <head>
    <meta charset="utf-8" />
    <title>Planos da Aurora | Aurora</title>
    <meta name="description" content="Planos da Aurora para equipes remotas." />
  </head>
  <body>
    <h1>Planos da Aurora</h1>
    <p>Escolha o plano que combina com a sua equipe.</p>
  </body>
</html>
```

**SSG (Static Site Generation)** — o build gera o HTML antes de qualquer
requisição. O resultado final é parecido com o do SSR, mas o servidor não faz
trabalho nenhum: ele só entrega arquivos que já estavam prontos.

A consequência prática do CSR é cara: para ler a sua página, o Google precisa
**renderizar o JavaScript** — a segunda etapa do pipeline que você viu no nó
`pipeline-da-busca`. Essa etapa é mais lenta que o rastreamento normal, roda
em uma fila separada, e em página com JavaScript pesado ou que depende de
interação, às vezes o render nunca chega a bom fim.

O que você fixa daqui:

- CSR entrega um shell; SSR e SSG entregam conteúdo.
- Se o texto não está no HTML inicial, você depende da etapa de rendering.
- **SSR ou SSG é o padrão.** CSR é uma escolha consciente, não um padrão.

O desenho acima é a regra geral, mas dá para ter **os dois**. As duas saídas
mais comuns hoje:

**Streaming (SSR com streaming)** — o servidor envia o HTML em pedaços, sem
esperar a página inteira. O `<head>` e o primeiro conteúdo chegam na hora; o
resto vem depois. Você ganha velocidade sem perder indexação.

**Partial prerender (SSG com re-render sob demanda)** — o build gera o HTML
estático das rotas públicas, e o servidor só renderiza de verdade quando
precisa (uma rota nova, um pedido de login). É o meio-termo que a maioria dos
frameworks modernos implementa.

O trade-off real, sem mythologia:

| | Complexidade | Indexação | Custo por request |
|---|---|---|---|
| CSR | baixa | depende da fila de rendering | barato |
| SSR | média | imediata | alto (o servidor renderiza) |
| SSG | média | imediata | quase zero (arquivo estático) |

E há um quarto caminho, o **híbrido**: o shell vem do build com o conteúdo
das rotas públicas já dentro, e só a parte que precisa de dados do usuário é
montada no navegador. É o que a maioria dos sites de conteúdo deveria usar.

> Nota: nem toda página precisa ser indexável. Um painel interno, uma área
> logada, uma tela de configuração — ninguém procura isso no Google. CSR é uma
> escolha boa e econômica para tudo que vive atrás do login.

## Pra quem quer ir além 🔴

Como conferir na prática o que o crawler recebeu? Abra o `view-source:` da sua
URL no navegador — é o HTML cru que o servidor entregou, sem executar
JavaScript. Se o seu texto principal não está ali, você já sabe o que
fazer.

No Search Console, a ferramenta "Inspeção de URL" mostra as duas etapas
separadas: o HTML que o Googlebot encontrou e o HTML **depois do
rendering**. A diferença entre as duas colunas é exatamente o custo do seu
CSR.

E um efeito colateral que costuma assustar: em CSR, o título e a meta
description às vezes são definidos por JavaScript, o que significa que
dependem de hydration. Se o JavaScript falhar, ou se o hydration receber um
HTML diferente do esperado, a página sobe com o conteúdo de outra rota —
o assunto de hydration mismatch é detalhado no nó `javascript-seo`.

## No seu projeto

- [ ] Abra `view-source:` da URL principal do seu site e leia o `<head>`: o title e a description estão lá, ou só aparecem depois que o JavaScript roda?
- [ ] Pegue o head que você montou no exercício, troque o título e a descrição pelos do seu produto e cole as tags no seu projeto — começando pelo `<title>` e pelo `<h1>`.

> Dica: se você usa Vite, Next.js, Nuxt ou Astro, nenhuma dessas tags exige
> biblioteca. É uma linha de template, no lugar certo do arquivo.
