Uma página diz "a Aurora custa 29 reais por mês". Um buscador lê aquilo como texto
e adivinha o resto. Quando a mesma página declara que aquilo é um
`SoftwareApplication` com um `Offer` de 29 BRL, o buscador para de adivinhar.
Este nó é o mapa do vocabulário que você vai usar nos próximos três.

## O essencial 🟢

Schema.org é um **vocabulário**: uma lista pública de tipos (`Organization`,
`Person`, `Article`, `Product`...) e de propriedades (`name`, `author`, `price`...)
que dizem exatamente o que cada uma significa. Nenhuma empresa "inventa" um
vocabulário: o Google, os buscadores e, cada vez mais, os modelos de IA leem o
mesmo dicionário.

Três peças resolvem quase tudo:

- `@type`: **o que** a coisa é.
- **propriedades**: os fatos sobre ela.
- `@id`: **quem** ela é.

```json
{
  "@context": "https://schema.org",
  "@type": "Organization",
  "name": "Aurora",
  "url": "https://aurora.test/",
  "logo": "https://aurora.test/logo.png",
  "sameAs": ["https://www.linkedin.com/company/aurora-exemplo"]
}
```

Esse bloco diz: existe uma entidade do tipo Organization, que se chama Aurora,
mora nesse endereço e tem esse logo. O `@context` é o que amarra o bloco ao
vocabulário — sem ele, as propriedades não significam nada.

### O `@id` é a identidade da entidade, não do documento

Esse é o ponto que mais confunde. O `@id` não identifica a página onde o bloco
aparece: identifica **a coisa descrita**. Se duas páginas (a home e a página
`/planos`, por exemplo) falam da mesma empresa, elas devem usar o mesmo `@id`:

```json
{ "@id": "https://aurora.test/#organizacao", "@type": "Organization", "name": "Aurora" }
```

A segunda página só referencia: `"publisher": { "@id": "https://aurora.test/#organizacao" }`.
O buscador costura as duas e entende que é a mesma empresa — em vez de duas
empresas parecidas.

### O grafo

Cada documento descreve entidades e liga elas por propriedades. É isso que
transforma um bloco de metadados em um grafo:

Repare que o grafo **não precisa estar inteiro numa página**. A página do
artigo descreve a pessoa e a organização; a home descreve a organização com
mais detalhes. Juntas, elas formam o retrato completo da Aurora.

> Nota: o `sameAs` liga a sua entidade a perfis externos — LinkedIn, GitHub,
> Wikipedia, Wikidata. É o que permite ao buscador casar "Aurora" com a empresa
> certa e não com a homotônima.

**O que fixar aqui:** `@type` diz o que é; `@id` diz de quem é; `sameAs` liga
a entidade ao mundo externo.

## Aprofundamento 🟡

### `@graph`: várias entidades em um único documento

Quando um documento descreve três ou mais entidades que se referenciam, o
padrão é um array `@graph`, no qual cada entidade é um objeto do grafo:

```json
{
  "@context": "https://schema.org",
  "@graph": [
    {
      "@id": "https://aurora.test/#organizacao",
      "@type": "Organization",
      "name": "Aurora",
      "logo": "https://aurora.test/logo.png"
    },
    {
      "@id": "https://aurora.test/#ana",
      "@type": "Person",
      "name": "Ana Ribeiro",
      "jobTitle": "Head de Produto",
      "worksFor": { "@id": "https://aurora.test/#organizacao" }
    },
    {
      "@id": "https://aurora.test/blog/kanban",
      "@type": "Article",
      "headline": "Kanban para equipes remotas",
      "author": { "@id": "https://aurora.test/#ana" },
      "publisher": { "@id": "https://aurora.test/#organizacao" }
    }
  ]
}
```

Lê assim: "a pessoa Ana, que trabalha para a organização Aurora, escreveu o
artigo X, publicado pela mesma organização". Uma empresa aparece uma vez, com
todas as suas propriedades; o resto só aponta para ela.

> Dica: a regra prática é **definir a entidade uma vez e referenciar**. Se você
> copiou a mesma organização com nome e logo em cinco blocos do site, você
> criou cinco entidades diferentes do ponto de vista do buscador.

### O vocabulário não é um formulário

Schema.org não valida nada: ele descreve tipos e suas propriedades, com
`domain` e `range` (onde a propriedade pode ser usada e que tipo de valor ela
aceita). `author` espera uma `Person` ou uma `Organization`; `author` apontando
para uma `Recipe` é sintaticamente aceito e semanticamente sem sentido.

Por isso existem ferramentas que checam o **perfil** que o consumidor espera
(o conjunto de campos que o Google recomenda para o `Article`, por exemplo).
Vocabulário é dicionário; perfil é o formulário que o buscador preenche.

### Por que isso importa mais para IA do que para rich result

Rich result é um bônus visual, exibição especial no Google. Entidade é
infraestrutura: é o que permite ao buscador — e a um modelo de linguagem que
resolve o assunto — saber que "Aurora" é uma empresa de organização de tarefas
com sede em São Paulo, que tem 40 pessoas, e que a pessoa que escreveu aquele
artigo é a Ana, que trabalha lá.

Você não precisa saber os centenas de tipos do Schema.org. Precisa saber que a maioria
dos sites se organiza em torno de meia dúzia deles: `Organization`, `Person`,
`Article`, `Product`, `FAQPage`, `BreadcrumbList`.

## Pra quem quer ir além 🔴

O grafo fica mais útil quando a mesma entidade aparece com propriedades
complementares em lugares diferentes. A página `/planos` da Aurora pode
descrever o `SoftwareApplication` e seus `Offer`; o blog descreve os
`Article`; a home liga os dois com `sameAs` e `publisher`.

Três hábitos que mantêm o grafo saudável:

1. **Um `@id` por entidade, guardado em um só lugar** no seu código (uma
   constante, uma função) — nunca `@id` digitado à mão em cada template.
2. **Nada de `sameAs` para perfil que não existe.** Ligar a um LinkedIn
   inexistente é pior do que não ligar.
3. **`@type` descreve a página, não o seu objetivo.** A página de preços é
   `Product` (ou `SoftwareApplication` com `offers`), não `Article` só porque
   você escreveu texto ali.

## No seu projeto

- [ ] Abra a home do seu site e liste as entidades que existem ali: a
      organização (ou a pessoa por trás do projeto), um produto ou serviço, e
      qualquer pessoa citada. Escreva um `@id` para cada uma e guarde esses
      `@id` em um arquivo único do seu projeto.
- [ ] Escreva um JSON-LD de `Organization` para o seu site com `name`, `url`,
      `logo` e pelo menos um `sameAs` de um perfil que exista de verdade. Depois
      valide no Schema Markup Validator e no Rich Results Test (ambos são
      ferramentas oficiais do Google e do Schema.org).

No próximo nó você escreve esse JSON-LD de verdade — e descobre por que um
erro de vírgula apaga o bloco inteiro.
