Esse é um dos "momentos uau" desta trilha. Se você levar **uma** coisa
deste nó, leve essa: **trate o prompt como código**. Rode, avalie, ajuste,
repita. Quem pensa assim, em poucas horas, faz mais do que quem passa
semanas "tentando achar o prompt perfeito de primeira".

## O loop de iteração

<Mermaid

/>

A parte que mais gente pula é a **3 (avaliar)** e a **4 (diagnosticar)**.
A reação natural a uma resposta ruim é "vou reformular tudo". Mas sem
diagnóstico, a reformulação vira tentativa-e-erro cega. Você gasta 30
minutos mexendo no escuro.

**O método:**

1. **Rode o prompt inicial** e anote (mentalmente ou num doc) o que veio.
2. **Liste 2-3 problemas concretos** da resposta. Seja específico: "o tom
   está formal demais", "faltou o critério X", "veio prosa, eu pedi tabela".
3. **Mapeie cada problema para a peça do prompt que deve corrigi-lo.**
   Use a anatomia do `seu-primeiro-prompt` como checklist:
   - Tom ruim → ajustar **persona** ou adicionar **restrições** de tom
   - Faltou informação → expandir **contexto**
   - Fez coisa que não devia → adicionar **restrição** ("NÃO faça X")
   - Formato errado → ajustar peça **formato**
   - Não entendeu a tarefa → simplificar **tarefa** ou quebrar em subtarefas
4. **Mude uma coisa por vez.** Se mudar três, não sabe qual ajudou.
5. **Rode de novo.** Compare. Repita até a resposta estar boa.
6. **Salve a versão final** com nome (v1, v2, ...). É seu histórico.

## Exemplo real: refinar um prompt de resumo executivo

**v1 (vago, vai mal):**
> "Resuma esse relatório."

**Resposta v1:** resumo de 3 parágrafos, foca em histórico, ignora
números-chave, tom acadêmico.

**Diagnóstico:**
- Falta contexto de público (pra quem é o resumo?)
- Falta critério de tamanho
- Falta diretiva sobre o que priorizar

**v2 (com anatomia, mas iterando):**
> "Você é um analista de negócios preparando um resumo executivo para
> o CEO, que tem 5 minutos pra ler.
>
> Resuma o relatório abaixo em 200 palavras, priorizando: (1) números
> e metas, (2) decisões tomadas, (3) próximos passos. Use tom direto e
> ativo. Termine com 1 bullet 'O que precisa de decisão do CEO'.
>
> Relatório: [colar]"

**Resposta v2:** muito melhor, mas ignorou o bullet final.

**Diagnóstico:**
- Pedido do bullet final ficou "solto" no fim. Modelo deu menos peso.

**v3:**
> (mesma v2, mas movido o bullet final para uma seção
> **"OBRIGATÓRIO"** no topo, depois da tarefa)

**Resposta v3:** atende tudo. Salva como v3.

Três iterações, não dez. Cada uma com mudança cirúrgica. **E você tem
v1, v2, v3 salvas** - se daqui a 6 meses alguém pedir "resumo
executivo" de novo, você não começa do zero.

## Versionar prompts em arquivo

Quando o prompt vira "reutilizável" (você usa 2+ vezes), ele merece um
arquivo. Convenção simples:

```
prompts/
  resumo-executivo/
    v1.txt
    v2.txt
    v3.txt
    notas.md   <- o que mudou entre versões e por quê
```

Você pode usar Git, Notion, Google Docs - qualquer coisa que dê
histórico. O ponto é: **se você está reescrevendo o mesmo prompt do
zero toda semana, está fazendo errado**.

- **Iterar é o trabalho real.** O primeiro prompt quase nunca é o
  melhor, e tá tudo bem.
- **Mude uma coisa por vez.** Se mudar três, não sabe qual ajudou.
- **Sempre diagnostique antes de mudar.** "O que veio + por que veio
  assim + o que eu queria" é a tríade.
- **Versione.** Salve v1, v2, v3. Você vai reaproveitar mais do que
  pensa.
- **Trate prompt como código**: rode, avalie, ajuste, repita. É o
  mesmo loop de TDD, só que o "teste" é subjetivo.

> Dica: o "mudar uma coisa por vez" parece ineficiente. Não é. É o
> atalho. Mexer em três coisas e rezar pra dar certo gasta mais
> tempo do que três ciclos de uma coisa por vez. Confie.

que vão te morder se você não souber delas. Honestidade sobre a
ferramenta é o que separa hobby de profissão.
